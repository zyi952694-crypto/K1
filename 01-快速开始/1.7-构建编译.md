# 1.7 构建编译

## 1. 前置准备

按 [1.1 硬件介绍](1.1-硬件介绍/index.md) 和 [1.2 系统烧录](1.2-系统烧录/index.md) 完成 K1 设备准备。板端构建使用 Bianbu 系统；交叉编译在 x86_64 Linux PC 上执行。

以下命令使用 Bash。SDK 默认放在 `~/spacemit_robot`，使用其他目录时请替换为实际路径。

### 1.1 可选：使用 Robot Skills 辅助环境搭建

如果使用 Codex、Claude Code 或 Cursor 等 coding agent，可以先安装 Robot Skills，让 Agent 辅助完成 SDK 获取、依赖检查、板端连接、开发模式选择和编译验证。Robot Skills 是可选辅助，不替代下文的手工命令。

在 Agent 对话框中直接给出仓库链接即可安装Robot skills：

```text
请安装 https://github.com/spacemit-robotics/robot-skills
```

如果通过 Agent 交互安装不成功，可在已安装 Node.js/npm 且能运行 `npx` 的环境中手动安装

```bash
# Codex
npx skills add spacemit-robotics/robot-skills --agent codex

# Claude Code
npx skills add spacemit-robotics/robot-skills --agent claude-code

# Cursor
npx skills add spacemit-robotics/robot-skills --agent cursor
```

Robot Skills 会按当前场景选择开发模式：

| 模式 | 适用场景 | SDK 位置 | 构建/运行位置 |
| :--- | :--- | :--- | :--- |
| local | Agent 直接运行在开发板上 | 开发板 | 开发板 |
| remote | Agent 在 PC 上，通过 SSH 使用开发板 | 开发板，PC 不需要下载 SDK | 开发板 |
| hybrid | PC 本地编辑，开发板构建运行 | PC 和开发板各一份；PC 默认 `~/workspace/spacemit-robot` | 开发板 |

remote 和 hybrid 模式下，Agent 会通过 SSH 登录开发板，在板端检查 SDK、安装依赖、编译和运行。Robot Skills 会先根据用户提供的 SSH 目标、端口、私钥或本机 SSH config 检查是否已经可以免密登录；如果尚未配置，会引导用户选择已有密钥或创建新密钥，并把公钥安装到开发板。这个过程通常需要用户确认目标地址，并可能在终端交互式输入一次开发板登录密码；Agent 不会保存密码，也不会要求用户把私钥内容写进对话。

首次使用时，安装好Robot-skill后建议先告诉 Agent（如codex、claude code）开发板 SSH 地址，例如：

```text
开发板地址是 bianbu@<K1_IP>，使用hybrid开发模式，请帮我搭建SDK环境。
```

示例中的 `<K1_IP>` 和登录用户应替换为实际值。

Agent 在执行 `sudo apt install`、`repo init`、`repo sync`、修改源配置或同步文件前，应先说明执行位置和影响范围，并等待用户确认。

### 1.2 后续章节如何使用

1.1 和后续章节是两种使用方式，不是需要全部叠加执行的步骤：

| 使用方式 | 后续章节怎么用 |
| :--- | :--- |
| 使用 SDK 手工搭建 | 跳过 1.1，从第 2 节开始按顺序执行。 |
| Agent 辅助 | 安装 Robot Skills 后，把开发板地址、SDK 状态和开发模式告诉 Agent；第 2 节及后续章节作为标准流程和命令核对依据，不需要逐条手动执行。 |
| 混合使用 | 可以让 Agent 先检查环境和生成命令，再由用户手工执行；同一个动作不要重复执行，例如不要手工执行一次 `repo sync` 后又让 Agent 再完整同步一次。 |
| 不使用 SDK | 如果只需要系统 ROS 2 和 Python 基础环境，执行 1.3；第 2 节及后续 SDK 获取、配置和编译步骤可跳过。 |

### 1.3 可选：不使用 SDK 时安装 ROS 2 与基础依赖

如果不使用 Robot SDK，只需要 ROS 2，可按本节准备最小 ROS 2 环境。若使用 Robot SDK 主流程，可跳过本节，继续执行第 2 节。

```bash
sudo apt update
sudo apt install \
  ros-humble-ros-base \
  ros-dev-tools \
  ros-humble-robot-localization \
  ros-humble-joint-state-publisher \
  ros-humble-tf-transformations
```

该最小环境不包含 RViz、Nav2、MoveIt、ros2_control 及其他图形或硬件相关组件。

后续在新终端中使用 ROS 2 时，先加载 Humble 环境：

```bash
source /opt/ros/humble/setup.sh
```

## 2. 代码获取

通过以下方式下载 Robot SDK 的全量仓库代码。GitHub 与 Gitee 是两种下载源，选择其中一种执行；用户名和邮箱替换为自己的信息：

```bash
sudo apt update
sudo apt install repo git

# 配置git用户名和邮箱（repo工具依赖git提交记录，需先配置）
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

mkdir -p ~/spacemit_robot
cd ~/spacemit_robot
```

方式一：使用 GitHub：

```bash
# 与方式二任选其一
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo
repo sync -j4
repo start robot-dev --all
```

方式二：使用 Gitee：

```bash
# 与方式一任选其一
repo init -u https://gitee.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo
repo sync -j4
repo start robot-dev --all
```

在新的空目录中，不加 `-g` 使用默认分组。已有按需下载工作区需要恢复全量下载时，重新执行 `repo init` 并显式添加 `-g default`，再执行 `repo sync -j4`。已有改动时先保存或提交修改。

若仅需部分源码，可在 **repo init 时使用 -g** 参数限定分组，再执行 **repo sync**；详见 **「5. 组合下载」** 章节。

## 3. 一键编译

本节默认使用板端环境编译。若需要在PC环境下编译构建，可参考后续小节选择 Docker 编译或交叉编译。

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal  # K1 最小方案；也可执行 lunch 交互选择
```

`lunch` 选择板型及产品方案。K1 提供 `k1-muse-pipro-minimal` 和 `k1-muse-pipro-ai-cubpet` 等方案；按应用需要选择。新开终端后需重新加载环境并选择方案。

### 3.1. 全量编译

```bash
cd ~/spacemit_robot
m
```

`m` 编译当前 target 中 `enabled_packages` 选中的包，不等于编译已下载 SDK 中的全部仓库。

### 3.2. 单组件编译

```bash
cd ~/spacemit_robot/components/peripherals/lidar
mm
```

上例编译雷达组件；其他组件替换为对应目录。`mm` 编译当前组件，`mm --with-deps` 会先构建其声明的 SDK 依赖。构建 ROS2 电机包时若提示 `Could not find ETHERCAT_LIB`，按第 6 节补装用户态库后重新构建。

编译完成后，产物按以下目录结构组织：可执行文件位于 `bin`、库文件位于 `lib`、头文件位于 `include`、配置文件位于 `share`。

普通编译和 Docker 编译的安装前缀为 `output/staging`。交叉编译会改用独立输出根目录，安装前缀为 `output/cross/<target>/staging`，详见 3.5。

### 3.3. 编译模式选择

Robot SDK 构建系统支持普通编译、Bianbu Docker 编译和交叉编译。三种模式使用同一套 `lunch`、`m`、`mm` 命令入口，但执行环境和输出目录不同。

| 模式 | 适用场景 | 执行环境 | 相对编译速度 | 安装前缀 | 运行部署目录 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 普通编译 | 在 K1 开发板上编译 | K1 当前系统 | 取决于板端资源 | `output/staging` | `output/rootfs` |
| Bianbu Docker 编译 | 需要尽量模拟板端 Bianbu 环境，或希望隔离系统依赖 | Bianbu riscv64 Docker 容器 | 较慢 | `output/staging` | `output/rootfs` |
| 交叉编译 | 在 x86_64 PC 上生成 riscv64 目标产物 | Ubuntu host 容器 + Bianbu sysroot 容器 | 较快 | `output/cross/<target>/staging` | `output/cross/<target>/rootfs` |

表中的速度描述为定性参考，不是性能测试结果。实际耗时受 CPU 核数、内存、存储、并行度和缓存影响。x86_64 PC 运行 riscv64 容器需要架构模拟；交叉编译的首次构建还有下载镜像、安装依赖和准备 sysroot 的开销。

运行部署目录由 `all` 全量编译结束时自动生成；如果只执行 `m -C`、`m -R` 或 `mm`，通常只更新安装前缀，需要部署目录时再执行 `./build/build.sh deploy-rootfs`，交叉编译则执行 `./build/cross_build.sh deploy-rootfs`。

Docker 编译和交叉编译都需要先安装 Docker，并确保 `docker info` 能正常连接服务。Ubuntu/Bianbu 可使用：

```bash
sudo apt update
sudo apt install docker.io
sudo systemctl enable --now docker
```

非 root 用户还需取得 Docker 使用权限；加入 `docker` 用户组后重新登录终端，再检查服务：

```bash
sudo usermod -aG docker "$USER"
# 重新登录后执行
docker info
```

x86_64 PC 还需配置 riscv64 的 QEMU/binfmt 支持，使 Docker 能运行 `linux/riscv64` 容器。K1 板端原生运行 riscv64 容器不需要此步骤。在 Ubuntu PC 上安装模拟器、加载注册配置，并检查实际注册状态：

```bash
sudo apt install qemu-user-static binfmt-support
sudo systemctl restart systemd-binfmt
cat /proc/sys/fs/binfmt_misc/qemu-riscv64
```

输出应包含 `enabled`，且 `flags` 中包含 `F`。若使用 `binfmt-support` 管理注册，可执行 `sudo update-binfmts --enable qemu-riscv64`；仅在 `update-binfmts` 中查不到记录，不代表内核未注册。

再通过 Bianbu 容器确认 riscv64 程序能够执行：

```bash
docker run --rm --platform linux/riscv64 \
    harbor.spacemit.com/bianbu/bianbu:2.3 uname -m
```

输出 `riscv64` 表示容器的架构模拟可用。

Docker 编译和交叉编译都是显式开关，`source build/envsetup.sh` 后默认关闭；同一个 shell 中不要同时启用两种模式。

### 3.4. Docker 编译

Docker 编译会把普通 `build/build.sh` 放入匹配目标板的 Bianbu 容器中执行，外部命令仍使用 `m` 和 `mm`。这不是交叉编译：编译器、系统依赖和 ROS 2 环境都来自 Bianbu 容器。

K1 target 默认使用 `bianbu:2.3`；本地没有镜像时，脚本会尝试拉取 `harbor.spacemit.com/bianbu/bianbu:2.3`。镜像由 target 的板型选择，无需修改构建脚本。

常用流程：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal

# 在当前 shell 启用 Bianbu Docker 编译
m_enable_docker_build

# 全量编译
m

# 只编译 CMake / non-ROS2 包
m -C

# 只编译 ROS 2 包
m -R
```

单组件 Docker 编译：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal
m_enable_docker_build

cd components/peripherals/lidar
mm
mm --with-deps
```

脚本或 CI 也可以对单次命令显式启用 Docker 编译：

```bash
cd ~/spacemit_robot
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k1-muse-pipro-minimal ./build/build.sh all
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k1-muse-pipro-minimal ./build/build.sh cmake
SROBOTIS_USE_DOCKER_BUILD=1 BUILD_TARGET=k1-muse-pipro-minimal ./build/build.sh package components/peripherals/lidar --with-deps
```

常用控制项：

| 命令 / 变量 | 说明 |
| :--- | :--- |
| `m_enable_docker_build` | 在当前 shell 启用 Docker 编译 |
| `m_enable_docker_build disable` | 在当前 shell 关闭 Docker 编译 |
| `SROBOTIS_DOCKER_CONTAINER_NAME=srobotis-k1-build` | 指定固定容器名，便于复用或排查 |
| `SROBOTIS_DOCKER_PLATFORM=linux/riscv64` | 覆盖 Docker 平台，默认即为 `linux/riscv64` |
| `SROBOTIS_DOCKER_DEVICES=/dev/xxx` | 需要访问宿主设备时透传 `/dev/*` 设备 |

Docker 容器默认会按 SDK 路径和 Bianbu 版本复用。Docker 编译不会创建独立的 `output/docker` 目录，构建中间目录、日志、安装前缀和部署目录仍写回当前源码目录下的 `output/`：

```text
output/
  build/     # CMake / ROS2 构建中间目录
  log/       # 构建日志
  staging/   # 安装前缀，m / m -C / m -R / mm 的主要安装输出
  rootfs/    # m all 或 deploy-rootfs 生成的运行部署目录
```

因此 Docker 编译后的运行、打包和部署路径与普通编译一致。切换普通编译与 Docker 编译时，若编译器或依赖版本不同，应在独立 SDK 工作区构建，或先清理当前工作区的构建产物，避免复用不兼容的 CMake 缓存。

> **注意**
>
> - 如需从 Docker 编译切换到交叉编译，先执行 `m_enable_docker_build disable`；反向切换时先执行 `m_enable_cross_build disable`。
> - 重新执行 `source build/envsetup.sh` 会关闭 Docker 编译和交叉编译开关，如需继续使用对应模式，需重新执行启用命令。

### 3.5. 交叉编译

交叉编译用于在 x86_64 PC 上构建 riscv64 目标产物，入口是 `build/cross_build.sh`。它会使用 Ubuntu host 容器执行 CMake、colcon、Cargo 等构建命令，并使用 Bianbu 容器安装目标依赖、导出 riscv64 sysroot。

常用流程：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal

# 在当前 shell 启用交叉编译
m_enable_cross_build

# 全量交叉编译
m

# 只交叉编译 CMake / non-ROS2 包
m -C

# 只交叉编译 ROS 2 包
m -R

# 按需清理当前 target 的交叉编译输出（会删除产物，默认不执行）
# m clean
```

单组件交叉编译：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal
m_enable_cross_build

cd components/peripherals/motor
mm
mm --with-deps
# 按需清理当前组件，默认不执行
# mm clean
```

脚本或 CI 可以直接调用 `cross_build.sh`，不依赖 shell 快捷函数：

```bash
cd ~/spacemit_robot
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh all
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh cmake
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh ros2
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh package components/peripherals/motor --with-deps
# 按需清理当前 target 的交叉编译输出，默认不执行
# BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh clean all
```

交叉编译输出目录如下：

```text
output/cross/<target>/
  build/                   # CMake / ROS2 构建中间目录
  log/                     # 构建日志
  host/                    # host 侧工具前缀
  sysroot/                 # 从 Bianbu 容器导出的 riscv64 目标 sysroot
  staging/                 # 交叉编译安装前缀，m / m -C / m -R / mm 的主要安装输出
  rootfs/                  # m all 或 deploy-rootfs 生成的运行部署目录
  toolchain-riscv64.cmake  # CMake toolchain file
  meson-riscv64.ini        # Meson cross file
```

可先查看交叉编译依赖拆分，不实际编译：

```bash
cd ~/spacemit_robot
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh deps all
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh deps package components/peripherals/motor
```

交叉编译完成后，可从 `staging` / `rootfs` 扫描 ELF 动态库并反推板端运行时 apt 依赖：

```bash
cd ~/spacemit_robot
BUILD_TARGET=k1-muse-pipro-minimal ./build/cross_build.sh runtime-deps all
```

常用控制项：

| 命令 / 变量 | 说明 |
| :--- | :--- |
| `m_enable_cross_build` | 在当前 shell 启用交叉编译，之后 `m` / `mm` 会转到 `build/cross_build.sh` |
| `m_enable_cross_build disable` | 在当前 shell 关闭交叉编译 |
| `SROBOTIS_CROSS_OUTPUT_ROOT=<dir>` | 覆盖默认输出目录 `output/cross/<target>` |
| `SROBOTIS_CROSS_REFRESH_SYSROOT=1` | 强制重新导出 sysroot，适用于 target 依赖变更后重新构建 |
| `SROBOTIS_CROSS_BIANBU_IMAGE=<image>` | 覆盖 Bianbu sysroot 镜像 |

### 3.6. 新增应用适配交叉编译

新应用通常放在 `application/native/<app>` 或 `application/ros2/<app>` 下。如果应用使用标准 CMake 或 ament CMake 构建，构建系统会自动传入 riscv64 toolchain、sysroot 和安装前缀，一般无需在应用中重复配置交叉编译器。

以下 `package.xml` 模板及 `<system_depend>` 属性适用于 SDK 的原生 CMake 应用。ROS2 ament 包应使用标准 ROS 包清单，不要直接套用这些扩展标签；SDK 的 ROS2 公共构建依赖由 `build/package_ros2.xml` 和 `build/package_ros2_cross.xml` 管理。

原生 CMake 应用适配时需完成以下配置：

1. 为应用提供 `package.xml`，用 `<depend>` 声明 Robot SDK 仓库内的组件依赖，用 `<system_depend>` 声明 apt 系统依赖。
2. 将运行库、头文件等目标依赖配置为 `realm="target"`，它们会安装到 Bianbu sysroot。不填写 `realm` 时，应用和组件的系统依赖默认也归属 target。
3. 将代码生成器和构建工具，例如 `protoc`、`grpc_cpp_plugin`、`moc` 和 Meson，配置为 `realm="host"`，它们会安装到 x86_64 Ubuntu host 容器。
4. 将应用路径加入目标方案的 `enabled_packages`。使用 `mm --with-deps` 时可以单独构建应用及其 SDK 依赖；使用 `m` 时则按 target 中的完整包集合构建。

例如，一个依赖 `motor` SDK 组件、protobuf 目标库和 host 侧 `protoc` 的 CMake 应用，可使用以下 `application/native/my_robot_app/package.xml`：

```xml
<?xml version="1.0"?>
<package format="3">
  <name>my_robot_app</name>
  <version>0.1.0</version>
  <description>My robot application</description>
  <maintainer email="maintainer@example.com">Your Name</maintainer>
  <license>Apache-2.0</license>

  <depend>motor</depend>
  <system_depend realm="target" check_kind="pkg-config" check_arg="protobuf">libprotobuf-dev</system_depend>
  <system_depend realm="host" check_kind="command" check_arg="protoc">protobuf-compiler</system_depend>

  <export>
    <build_type>cmake</build_type>
  </export>
</package>
```

请将维护者信息和许可证替换为项目实际信息。

`<system_depend>` 还可以使用以下属性：

| 属性 | 说明 |
| :--- | :--- |
| `when="cross"` | 仅在交叉编译时使用该依赖；`native` 和 `docker` 可用于排除交叉编译 |
| `realm="host \| target \| both \| skip"` | 分别表示 host 工具、target sysroot 依赖、两侧都安装或交叉编译时忽略 |
| `arch="riscv64"` | 仅在当前 realm 的架构匹配时使用 |
| `check_kind` / `check_arg` | 指定依赖检查方式和参数，支持 `dpkg`、`command`、`pkg-config`、`file` 和 `rustlib` |

再将应用加入 target 配置的 `enabled_packages`，保留原有板型、产品和其他选项。以下是需要合并的字段：

```json
{
  "enabled_packages": [
    "components/peripherals/motor",
    "application/native/my_robot_app"
  ]
}
```

例如，复制 `target/k1-muse-pipro-minimal.json` 为 `target/k1-muse-pipro-my-robot.json`，将 `product` 改为 `my-robot`，并在原有 `enabled_packages` 中追加 `application/native/my_robot_app`。完成应用源码及 CMake 安装规则后，先检查依赖拆分，再进行单应用构建：

```bash
cd ~/spacemit_robot
BUILD_TARGET=k1-muse-pipro-my-robot ./build/cross_build.sh deps package application/native/my_robot_app
BUILD_TARGET=k1-muse-pipro-my-robot ./build/cross_build.sh package application/native/my_robot_app --with-deps
```

当应用的 CMake 工程内部还使用 `ExternalProject_Add` 启动新的 CMake 配置过程时，子工程不会自动继承顶层 toolchain，需将 `SROBOTIS_CMAKE_EXTRA_ARGS` 转换为 CMake 参数列表并传入子工程的 `CMAKE_ARGS`。如果子工程使用 Meson，需传入 `--cross-file "${SROBOTIS_MESON_CROSS_FILE}"`。对于需要在构建期运行的工具，应明确使用 host 侧可执行文件，不要尝试运行 sysroot 中的 riscv64 程序。

## 4. 方案配置

根据所选方案，可在对应的配置文件中启用或禁用组件/包的编译。若需排除特定包，将其从配置中移除即可。

```bash
cd ~/spacemit_robot
ls target/k1-*.json
```

以 `k1-muse-pipro-minimal.json` 为例：

```json
{
  "version": "1.0",
  "board": "k1-muse-pipro",
  "product": "minimal",
  "description": "K1 MUSE PIPRO board - minimal build configuration",
  "enabled_packages": [
    "components/peripherals/motor",
    "components/peripherals/lidar"
  ],
  "enabled_package_options": {
    "components/peripherals/motor": { "enabled_drivers": ["drv_can_dm"] },
    "components/peripherals/lidar": { "enabled_drivers": ["drv_uart_ydlidar", "drv_uart_rplidar"] }
  },
  "options": {
    "parallel_jobs": 4,
    "auto_resolve_dependencies": true
  }
}
```

该模板对应 K1 最小方案，启用 CAN 电机驱动和两种串口雷达驱动。`enabled_packages` 选择构建包，`enabled_package_options` 选择驱动，`parallel_jobs` 设置构建并行度，`auto_resolve_dependencies` 控制系统依赖自动安装。选择其他驱动时同步调整包选项和依赖。

修改配置文件后，重新执行 `lunch <target>` 选择该方案，然后再编译。

## 5. 组合下载

若无需下载全量 SDK，可按场景按需下载所需的包。只需在 `repo init` 命令末尾追加 `-g` 参数指定要下载的软件包分组，具体示例如下：

以下命令在 `~/spacemit_robot` 目录执行，按需选择其中一种分组。

```bash
cd ~/spacemit_robot

# 只下载AI相关的应用：Model Zoo + ai-gateway
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,model_zoo,ai-gateway
repo sync -j4
repo start robot-dev --all

# 只下载人型应用：人形全套（humanoid + model_zoo_rl + simulation，仿真见 manifest component/simulation.xml）
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,model_zoo_rl,humanoid,simulation
repo sync -j4
repo start robot-dev --all

# 只下载桌面机器人应用： Reachy mini
repo init -u https://github.com/spacemit-robotics/manifest.git -b main -m default.xml \
  --repo-url=https://gitee.com/spacemit-robotics/git-repo \
  -g core,peripherals,multimedia,model_zoo,agent_tools,reachy_mini
repo sync -j4
repo start robot-dev --all
```

Reachy Mini 的包依赖包含音频和 Model Zoo 组件，因此下载分组同时包含 `multimedia` 和 `model_zoo`。

按需分组一览（`-g` 仅在 `repo init` 时指定，随后的 `repo sync -j4` 与第 2 节一致，最后执行 `repo start robot-dev --all`）：

| 序号 | 场景 | repo init 追加 -g（接在 §2 同一条 init 命令末尾） |
| :--- | :--- | :--- |
| 0 | 全量下载 | 新工作区不加 -g；已有分组工作区使用 -g default |
| 1 | 人形全套 | -g core,model_zoo_rl,humanoid,simulation |
| 2 | 人形指定机型 | -g core,model_zoo_rl,humanoid_common,humanoid_unitree_g1,simulation |
| 3 | 桌面 Reach mini | -g core,peripherals,multimedia,model_zoo,agent_tools,reachy_mini |
| 4 | 轮式 Linksee | -g core,ros2,linksee |
| 5 | 语音交互 Omni | -g core,multimedia,model_zoo,agent_tools,omni_agent |
| 6 | Model Zoo + ai-gateway | -g core,model_zoo,ai-gateway |
| 7 | 外设驱动基础 | -g core,peripherals,agent_tools |
| 8 | 机器人感知 | -g core,model_zoo,ros2_perception |
| 9 | 机器人外设 | -g core,peripherals |
| 10 | 规划、控制 | -g core,multimedia,model_zoo,control,ros2_planning,ros2_control |

分组用于选择下载范围，不代表对应机器人产品已完成 K1 适配。按需下载时应覆盖所选 target 的全部组件及其依赖；缺少仓库时补充分组后再同步。

完整分组定义以 manifest 仓库各 `.xml` 文件中 `groups="..."` 属性为准；片段路径参见 `default.xml` 中的 include 配置。

## 6. 常见问题

目录无效：

```
[mm] ERROR: Not a valid package directory
[mm] Hint: Run mm from a directory with CMakeLists.txt, package.xml, or build.sh
```

当前目录不是有效的组件目录。请确认目录中包含以下标识文件之一；同时存在多个标识时，依次优先使用可执行的 `build.sh`、`package.xml` 中的 ament 构建类型和 `CMakeLists.txt`：

| 目录标识 | 编译逻辑 | 支持的路径示例 |
| :--- | :--- | :--- |
| **存在 `CMakeLists.txt`，且未命中自定义脚本或 ament 构建类型** | 原生 CMake 编译 | `components/peripherals/motor`, `application/native/*` |
| **存在执行权限的 `build.sh`** | 自定义脚本编译 | 任何含有 `build.sh` 的子目录 |
| **`package.xml` 的 `build_type` 为 `ament_cmake` 或 `ament_python`** | ROS2 (colcon) 编译 | `middleware/ros2/*`, `application/ros2/*` |

其他常见情况：

| 现象 | 处理 |
| :--- | :--- |
| `m -R` 提示没有启用的 ROS2 包 | 检查所选 target 的 `enabled_packages`。K1 minimal 只启用原生电机和雷达组件；需要 ROS2 时加入对应 ROS2 包路径，或进入包目录执行 `mm --with-deps`。 |
| Docker 命令不存在或不能连接服务 | 按 3.3 安装并启动 Docker，确认当前用户执行 `docker info` 成功。 |
| 在 x86_64 PC 启动 riscv64 容器时报 `exec format error` | 检查 QEMU/binfmt 的 riscv64 注册是否启用，并使用 `linux/riscv64` 容器平台。 |
| 按需下载后构建提示缺少组件目录 | `repo` 分组不会根据 `package.xml` 自动补齐 SDK 依赖；补充分组，重新 `repo init -g ...` 和 `repo sync -j4`。 |
| 更换 SDK 路径后出现 CMake 缓存错误 | 在新目录重新加载 `build/envsetup.sh` 和选择 target，并重新构建；不要复制旧工作区的 `output/build`。 |

**ROS2 电机包构建时找不到 EtherCAT 库**

当前 ROS2 电机包的构建文件会查找 IgH EtherCAT 用户态库。若提示 `Could not find ETHERCAT_LIB`，可按以下步骤补装依赖，保留原始 `CMakeLists.txt`。

以下命令在 K1 板端执行，将 IgH EtherCAT 1.6.13 用户态库安装到 `~/.local/etherlab`。已下载该版本源码时，可跳过 `git clone`：

```bash
sudo apt update
sudo apt install build-essential git autoconf automake libtool pkg-config

mkdir -p ~/src
git clone --depth 1 --branch 1.6.13 \
    https://gitlab.com/etherlab.org/ethercat.git ~/src/ethercat-1.6.13
cd ~/src/ethercat-1.6.13

./bootstrap
./configure --prefix="$HOME/.local/etherlab" \
    --disable-kernel --disable-tool
make -C lib -j4
make -C lib install
make -C include install
```

加载 SDK 环境后，设置编译及运行时的库搜索路径，并重新构建 ROS2 电机包：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch k1-muse-pipro-minimal

export CMAKE_PREFIX_PATH="$HOME/.local/etherlab${CMAKE_PREFIX_PATH:+:$CMAKE_PREFIX_PATH}"
export LD_LIBRARY_PATH="$HOME/.local/etherlab/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"

cd middleware/ros2/peripherals/motor
mm --with-deps
```

新开终端后，需重新加载 SDK 环境并执行上述两个 `export` 命令。检查程序的动态库依赖前，还需加载 ROS2 环境：

```bash
source /opt/ros/humble/setup.bash
ldd ~/spacemit_robot/output/staging/lib/peripherals/motor_node
```

输出中不应出现 `not found`。上述步骤只安装用户态库及头文件，不包含 EtherCAT 内核模块或主站服务；实际 EtherCAT 设备通信需另行准备相应驱动与硬件。

## 附录：常用编译命令

在仓库根目录加载环境并选择构建目标后，即可执行编译命令生成各组件的示例应用。

| 场景 | 编译命令 | 清理命令 | 说明 |
| :--- | :--- | :--- | :--- |
| 全量编译 | `m` | `m clean` | 编译当前 target 启用的包 |
| 只编译 CMake 包 | `m -C` | `m -C clean` | 跳过 ROS2 包 |
| 只编译 ROS2 包 | `m -R` | `m -R clean` | 仅编译所选方案中的 ROS2 包；方案未启用时跳过 |
| 单组件编译 | `cd 组件目录 && mm` | `mm clean` | 编译当前目录组件 |
| 回到仓库根 | `croot` | — | 在任意子目录执行后 `cd` 到 SDK 根目录（与 `source build/envsetup.sh` 后环境配套） |

`m clean` 会清理当前模式的构建产物，普通模式还会删除默认的 `output/staging` 和 `output/rootfs`。仅需清理单个组件时使用 `mm clean`；清理后需重新构建。
