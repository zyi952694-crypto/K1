# 基础传感器 · 光感

## 1. 模块概述

光感模块位于机器人开发层的基础传感器能力中，对下封装 `components/peripherals/light_sensor` I2C 光照传感器组件，对上提供 ROS 2 节点 `light_sensor_node` 和光照话题。模块用于周期性读取传感器 lux 值，并以标准 ROS 2 传感器消息发布给上层应用、感知算法或环境自适应逻辑订阅使用。

**规格与特性**

对外直接复用标准消息 `sensor_msgs/msg/Illuminance`，默认话题名为 `/light_sensor/lux`；节点名固定为 `light_sensor_node`；发布 QoS 使用 `rclcpp::SensorDataQoS()`；默认采样与发布频率 `5 Hz`；默认驱动名为 `W1160`，默认 I2C 设备节点 `/dev/i2c-3`、默认地址 `0x48`；支持通过参数配置 `frame_id`、话题名、方差和轮询频率。该模块没有自定义私有 `msg/srv`，因此不依赖共享接口包。底层依赖 `light_sensor.h`、静态库 `liblight_sensor.a`、厂商静态库 `libstk_alps_lib.a` 与 I2C 设备节点 `/dev/i2c-*`。

## 2. 环境准备

### 前置条件

**运行环境**

- 开发板：K1 MUSE Pi Pro
- 系统：Bianbu 2.3.5，Linux 6.6.63
- ROS 2 环境：Humble
- 构建侧需要 CMake、C++17 编译器、`ament_cmake`、`rclcpp`、`sensor_msgs` 和 SDK 统一构建脚本

**依赖与外部资源**

本模块依赖 Linux I2C 字符设备接口，不需要额外第三方动态库。W1160 驱动依赖仓库内自带的 `src/drivers/drv_i2c_w1160/libstk_alps_lib.a` 静态库，构建时可能需要 `-fno-pie` 选项避免位置无关代码链接错误。

**硬件与连接**

需要一颗通过 I2C 连接的 W1160 光照传感器。K1 扩展板上焊接的 W1160 连接至 **I2C-3，地址 0x48**。确认传感器已正确供电，SCL/SDA 已连接到目标板对应 I2C 控制器。

**工具与权限**

排查问题时建议预装 `apt install i2c-tools`，使用 `i2cdetect`/`i2cdump` 等工具排查问题。

### 构建编译

**获取代码**

详见 [2.3-配置编译](../../02-快速入门/2.3-配置编译.md#21-代码获取) 章节，使用 `repo` 工具克隆完整 SDK。以下编译测试命令均在 SDK 内执行。

**本模块编译**

按依赖顺序先编译底层光感组件，再编译 ROS 2 节点包：

```bash
cd ~/spacemit_robot
source build/envsetup.sh
lunch  # 选择 k1-muse-pipro-minimal

cd components/peripherals/light_sensor
rm -rf build build-nopie
mkdir build-nopie && cd build-nopie
cmake .. -DBUILD_TESTS=ON -DCMAKE_C_FLAGS="-fno-pie" -DCMAKE_EXE_LINKER_FLAGS="-no-pie"
make -j$(nproc)
sudo cp test_light_sensor_i2c ~/spacemit_robot/output/staging/bin/

cd ~/spacemit_robot
./build/build.sh package middleware/ros2/peripherals/light_sensor
```

预期产物包括：
- `output/staging/lib/peripherals_light_sensor_node/light_sensor_node`
- `output/staging/share/peripherals_light_sensor_node/params/light_sensor_node_k1.yaml`

## 3. 示例使用

### 3.1 底层测试

在启动 ROS 2 节点前，建议先用底层组件排除 I2C 和硬件问题。

**步骤 1**：确认 I2C 设备可见

```bash
i2cdetect -y 3
```

预期在地址 `0x48` 处看到设备应答（显示 `48`）。

**步骤 2**：运行底层测试程序

```bash
sudo ~/spacemit_robot/output/staging/bin/test_light_sensor_i2c /dev/i2c-3 0x48
```

预期输出类似：

```text
W1160 Light Sensor I2C Test
Using: dev=/dev/i2c-3 addr=0x48
W1160 initialization OK, polling light values...
[0] Light value: 567 lux
[1] Light value: 569 lux
[2] Light value: 568 lux
...
```

如果底层测试无法稳定打印 lux 值，优先检查 I2C 总线号、设备地址、供电和接线。

### 3.2 ROS 2 节点

**步骤 1**：加载 ROS 2 环境

```bash
source /opt/ros/humble/setup.bash
source ~/spacemit_robot/output/staging/setup.bash
```

**步骤 2**：检查参数文件

K1 参数文件位于 `output/staging/share/peripherals_light_sensor_node/params/light_sensor_node_k1.yaml`，关键参数：

```yaml
light_sensor_node:
  ros__parameters:
    driver: W1160
    name: als0
    device: /dev/i2c-3
    i2c_addr: 72          # 0x48 的十进制
    topic: light_sensor/lux
    frame_id: light_sensor
    variance: 0.0
    poll_hz: 5.0
```

**步骤 3**：启动节点

```bash
ros2 run peripherals_light_sensor_node light_sensor_node \
  --ros-args \
  --params-file ~/spacemit_robot/output/staging/share/peripherals_light_sensor_node/params/light_sensor_node_k1.yaml
```

预期现象：终端打印类似日志，表示节点已启动并完成底层设备初始化。

```text
light_sensor_node ready: driver=W1160 name=als0 device=/dev/i2c-3 addr=0x48 topic=light_sensor/lux poll_hz=5.000
```

**步骤 4**：订阅光照话题

另开一个终端，加载同样的 ROS 2 环境并订阅光照话题。由于发布端使用 `SensorDataQoS`，建议显式指定 `best_effort`。

```bash
source /opt/ros/humble/setup.bash
source ~/spacemit_robot/output/staging/setup.bash

ros2 topic echo /light_sensor/lux --qos-reliability best_effort
```

预期现象：终端能看到 `sensor_msgs/msg/Illuminance` 输出，例如：

```yaml
header:
  stamp:
    sec: 0
    nanosec: 0
  frame_id: light_sensor
illuminance: 567.0
variance: 0.0
---
```

**步骤 5**：改变环境光照

遮挡传感器、移动到强光环境或用手电照射后，`illuminance` 字段应发生明显变化。若短时间内没有新消息，但节点也没有报错，可能是底层 `light_sensor_poll()` 暂时返回了 `-EAGAIN`，当前节点会直接跳过本次发布。

## 4. 应用开发

**对外 API 或接口形态**

上层应用主要订阅 ROS 2 话题 `/light_sensor/lux`，消息类型为 `sensor_msgs/msg/Illuminance`。消息字段包括 `std_msgs/Header header`、`float64 illuminance` 和 `float64 variance`。当前节点不提供 service，也不提供 action；光照值属于连续传感器数据，适合用话题流式分发。

**调用方式与注意点**

- 节点内部通过定时器主动调用 `light_sensor_poll()` 轮询底层数据，而不是由底层中断或回调推动。
- 发布端使用 `rclcpp::SensorDataQoS()`；在某些 ROS 2 工具或自定义订阅端上，如果使用默认 `reliable` QoS，可能看不到数据，建议订阅端显式使用与传感器数据兼容的 QoS。
- `driver` 和 `name` 会组合成底层实例名，例如默认组合后是 `W1160:als0`。如果 `driver` 不存在，`light_sensor_alloc_i2c()` 会失败，节点会抛出 `light_sensor_alloc_i2c failed`。
- `i2c_addr` 必须在 `[0, 127]`，`poll_hz` 必须大于 `0`，`variance` 必须大于等于 `0`；`device`、`driver` 和 `name` 不能为空。
- 当前 ROS 2 节点只封装了 `light_sensor_alloc_i2c()`，因此实际支持的是 I2C 传感器路径。
- 当底层 `light_sensor_poll()` 返回 `-EAGAIN` 时，节点会直接跳过本次发布且不打印告警；只有返回其他错误码时，才会每 `2 s` 节流打印一次 `light_sensor_poll failed`。
- 节点析构时会自动调用 `light_sensor_free()` 释放底层资源；应用侧只需正常退出 `light_sensor_node`，不需要直接干预底层生命周期。

## 5. 调试指南

- **先用底层组件排除 I2C 和硬件问题**：运行 `sudo test_light_sensor_i2c /dev/i2c-3 0x48`。如果底层测试无法稳定打印 lux 值，优先检查 I2C 总线号、设备地址、供电和接线。
- **使用 `i2cdetect -y 3`、`i2cget` 等工具**：确认设备是否出现在预期总线上；如果节点启动时报 `light_sensor_init failed`，常见原因是设备节点错误、地址错误、I2C 权限不足，或底层 W1160 驱动初始化失败。
- **观察节点日志**：正常启动应看到 `light_sensor_node ready`。如果参数非法，程序会在标准错误输出打印 `light_sensor_node exception: ...`。
- **观察 ROS 2 图和话题**：使用 `ros2 node list` 确认存在 `/light_sensor_node`，使用 `ros2 topic list | grep light_sensor` 确认话题存在，使用 `ros2 topic echo /light_sensor/lux --qos-reliability best_effort` 查看数据，使用 `ros2 topic hz /light_sensor/lux` 粗略观察实际发布速率。
- **如果节点运行中完全没有消息**：但也没有报错，需要考虑底层持续返回 `-EAGAIN` 的情况。这通常意味着驱动当前没有准备好新样本，可先降低 `poll_hz`，再结合底层测试程序观察是否能得到有效数据。

## 6. 常见问题

**Q: 底层测试正常，但 ROS 2 节点无数据？**

A: 检查 QoS 兼容性，订阅端显式指定 `--qos-reliability best_effort`。检查参数文件中 `device` 和 `i2c_addr` 是否正确。

**Q: 编译报链接错误 `relocation R_RISCV_HI20`？**

A: W1160 驱动依赖的 `libstk_alps_lib.a` 静态库需要 `-fno-pie` 选项。按照本文档 2.2 节重新编译底层组件。

**Q: 光照值不随环境变化？**

A: 确认扩展板与 K1 连接稳定，光感表面未被遮挡。使用底层测试程序单独验证传感器响应。
